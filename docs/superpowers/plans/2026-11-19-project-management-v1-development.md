# superPM 项目管理 V1 开发文档

日期：2026-11-19（Asia/Shanghai）。

更新：2026-11-21（Asia/Shanghai）。S0—S4 开发收尾与六项遗留缺陷修复已完成；1.3.0 版本分发与真实包发布前验证见第 22 节。

## 1. 目标、依据与交付范围

在现有需求管理之上增加轻量项目容器，让项目经理、产品经理、开发和测试使用各自账号，在同一服务实例内完成“目标 → 需求 → 执行 → 交付 → 验收 → 结项”。创建项目只要求填写名称，其余信息随推进补充。

已确认的方向是团队协作、轻量项目信息，以及项目概览效果图的总体布局。本文将这一方向落实为数据、权限、接口和开发顺序；新增技术约定列在第 16 节，后续调整需要同步文档与测试。

- 产品依据：[项目管理 V1 产品设计初稿](../specs/2026-11-19-project-management-v1-draft.md)。
- 视觉依据：[项目概览效果图](../../../outputs/project-management-v1-overview.png)、[独立 HTML 样稿](../../../outputs/project-management-v1-overview.html)。图片是最终 V1 的示例布局，不是当前已实现能力。
- 现存问题：[2026-11-19 Bug 审查表](../../reviews/2026-11-19-bug-audit.md)。
- 开发前基线：`main / 1e94a0d`，应用 `1.2.0`，原最新数据库迁移 `0021_requirement_pins.sql`。S1 新增 `0022_projects.sql`；本轮不调整正式版本号。

### V1 包含

项目列表与详情、项目成员和角色、需求归属与责任人、需求资料共享、跨日项目任务、个人今日安排关联、默认交付与多批交付、范围版本、验收与结项、项目概览和动态。

### V1 以外

合同、预算、回款、采购、企业组织架构、外部客户账号、客户门户、复杂审批、甘特依赖、资源负载、Git/CI 自动流转、跨实例同步。现有本地服务不会因开发项目协作而自动改为外网监听。

## 5. 数据模型

以下为目标逻辑结构，只有对应阶段的迁移落地后才算实际表。新增表有明确的项目权限策略；不能照搬“加 user_id 并放进 SCOPED_TABLES”而将同项目成员再次隔离。迁移测试须核对新增业务表均已归入个人、需求子资源或项目访问策略，未知表不能默认为共享。

### S1：项目和需求共享

| 表/字段                   | 主要字段                                                                                                                                                                                                                                           | 约束与说明                                                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`                | id, project_no, name, goal, scope_summary, customer_name, customer_contact, planned_start_date, target_delivery_date, owner_user_id, product_owner_user_id, status, previous_status NULL, version, archived_at, created_by, created_at, updated_at | project_no 全局唯一；名称 1—200 字；创建者默认兼任两负责人；version 从 1 起；无硬删除入口                                               |
| `project_members`         | project_id, user_id, status, joined_at, removed_at                                                                                                                                                                                                 | 复合主键；status 为 active/removed；历史身份保留                                                                                        |
| `project_member_roles`    | project_id, user_id, role                                                                                                                                                                                                                          | 复合唯一，外键指向成员；一人可有多个角色                                                                                                |
| `project_events`          | id, project_id, action, actor_user_id, actor_name_snapshot, payload, created_at                                                                                                                                                                    | 追加式；关联对象信息保留在 JSON payload 中，无独立 entity_type/entity_id 列；事务与业务修改同成败，不写口令/令牌或整篇私人内容          |
| `project_commands`        | id, project_id NULL, actor_user_id, idempotency_key, command, request_hash, response, created_at                                                                                                                                                   | response 为结果 JSON；actor_user_id/command/idempotency_key 联合唯一，约束不依赖可空 project_id；同键不同目标或入参拒绝，创建后绑定项目 |
| `requirements` 新列       | project_id NULL, assignee_user_id NULL, developer_user_id NULL, acceptance_criteria TEXT, version INTEGER                                                                                                                                          | 旧数据 project_id 为 NULL；user_id 保持旧归属；version 从 1 起                                                                          |
| `deliveries` 最小计划容器 | id, project_id, name, is_default, status, version, created_by, created_at, updated_at                                                                                                                                                              | 在 S1 建表；project_id 在 is_default=1 时部分唯一；S1 只创建 planning 记录                                                              |

项目负责人字段表示主要联系人；拥有 owner 角色的成员可以有多名。主要负责人必须是 active 且具有 owner 角色，产品负责人同理必须具有 product_owner 角色。变更主要负责人、移除角色和移除成员在一个事务内校验，不能留下无负责人的项目。

项目编号使用独立序列 PRJ-0001，不依赖当前用户可见的最后一行；在写事务内分配，并有唯一索引兜底。需求 REQ 编号、ID、URL 和目录映射均不重排。

项目基础创建不立即创建物理目录。成员管理改变项目 version，避免两个管理员用旧快照相互覆盖。需求主子树的 project_id 必须一致；改 parentId、增加子项、软删除同样经过项目及交付范围校验。

历史/审计新增 nullable actor_user_id 和操作者显示名快照；存量无法识别的 local-user 保持“历史操作者未知”，不能回填成迁移人。所有新的动作从认证上下文取操作者，拒绝客户端自报身份。

共享后可变的问题和资源元数据（issues、artifact_nodes、artifact_links、旧 requirement_files）也增加整数 version，不能只锁需求主表。文件/问题正文另用内容哈希；追加式评论和活动不允许修改原记录，通过幂等键防重复追加。

### S2：执行与工时

| 表/字段                    | 主要字段                                                                                                                                                                                     | 约束与说明                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `project_tasks`            | id, project_id, requirement_id NULL, title, description, type, assignee_user_id, confirmer_user_id, due_date NULL, status, previous_status NULL, version, created_by, created_at, updated_at | 关联需求时必须为同项目叶子需求；任务可跨日；确认人和执行人是 active 非只读成员 |
| `project_task_submissions` | id, task_id, submitted_by, summary, evidence_json, created_at                                                                                                                                | 每次提交追加，证据是已授权的资源引用或安全外部链接                             |
| `project_task_reviews`     | id, submission_id, reviewer_user_id, result, reason, created_at                                                                                                                              | 通过/退回均追加；一次提交最多一个有效确认结论                                  |
| `daily_tasks` 新列         | project_task_id NULL                                                                                                                                                                         | 主体仍属个人；有工时后不可静默改来源                                           |
| `daily_time_entries` 新列  | project_id NULL, project_task_id NULL                                                                                                                                                        | 开始计时时写入来源快照，不按今天的任务关联反推历史工时                         |

同一账号、同一项目任务、同一业务日最多一个未删除的个人安排，使用部分唯一索引防双击重复。一个项目任务可以有多天安排。项目工时以有明确来源的工时记录 ID 去重聚合；未关联的旧记录不自动归入项目。

移除成员或停用账号后，其个人已记录工时不删除。项目只聚合明确共享的工时数据，不公开个人便签、工作总结和未关联日程。退出项目后，个人日安排可保留自己的既有文本和时长，但不能再解析无权访问的项目标题、需求内容或附件。

### S3：交付与验收

| 表                           | 主要内容                                                                      | 不变量                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `deliveries` 扩展            | 计划/实际交付日、验收人、current_scope_version_id、交付说明                   | 扩展 S1 已建的容器；每项目唯一默认交付；同一交付最多一个有效待验收轮次    |
| `delivery_scope_versions`    | delivery_id、递增范围版本、确认人、确认时间、变更原因                         | 确认后不可覆盖；修订生成下一版本                                          |
| `delivery_scope_items`       | scope_version_id、requirement_id、需求编号/名称/正文/验收标准/对象版本快照    | 只接受叶子需求；每个版本同一需求唯一                                      |
| `delivery_scope_changes`     | 新增/取消/延期/豁免、原范围项、原因、批准人、后续去向/责任人/跟进日           | 移出当前版本不等于抹除过去承诺；结项仍检查处置记录                        |
| `delivery_assignments`       | project_id、delivery_id、requirement_id、released_at                          | 对 released_at IS NULL 的 requirement_id 建唯一索引，防重复承诺到并行批次 |
| `delivery_acceptance_rounds` | delivery_id、scope_version_id、交付版本说明、证据快照、发起人、时间、轮次结果 | 绑定提交时的范围版本；已结束轮次不可改写                                  |
| `delivery_acceptance_items`  | round_id、scope_item_id、通过/不通过/豁免、原因、问题引用、实际确认人         | 一轮一项唯一；退回原因/问题不可缺失                                       |
| `delivery_issue_links`       | delivery_id、issue_id、is_blocking、影响说明、标记人、version                 | 同交付/问题唯一，需求必须同项目；标记/取消标记留事件                      |
| `delivery_risk_acceptances`  | 阻断关系 ID、issue_version、原因、接受人、接受时间、证据快照                  | 追加式；仅 owner 可接受；问题重要修改后旧版本风险接受不再覆盖新风险       |
| `project_closures`           | project_id、结项/重开、检查摘要、结论、操作者、时间                           | 保留每次结项与重开历史                                                    |

交付证据若只是可变文档链接，不能声称历史不变。提交验收时保存证据的描述、来源资源 ID、内容哈希，并为需保留的文本/附件创建不可变快照；新增快照位于独立的受保护项目资源区域，不移动或覆盖原需求文件。快照失败则提交失败，不留下“已提交但缺证据”的记录。

验收结果另支持客户确认人姓名、身份说明、客户确认时间和确认凭证快照；这些是内部录入的外部确认信息，不是新账号，也不能替代来自认证上下文的 recorded_by。界面同时显示“客户确认人”和“系统录入人”，内部验收可以不填写客户字段。

范围修订时，在同一事务内使旧的待验收轮次失效、追加 superseded 事件并将交付退回 active；旧轮次与结果保留。提交结果必须同时匹配交付 expectedVersion、未结束轮次和 current_scope_version_id；迟到的旧范围结果返回 409，不能把新范围标成 accepted。V1 新范围版本的当前承诺项重新确认，不自动搬用历史通过结果。

项目新建时生成默认交付记录的 S1 行为只建立计划容器；S3 前不开放范围或验收接口，也不展示示例进度。多批交付按需新增，不要求先建批次才能工作。

### S4：项目资料

`project_documents` 保存项目说明、会议纪要/决策、外部链接及其版本和操作者。首版资料页支持项目笔记/链接，以及需求产物的授权聚合；不再建第二套需求 PRD。私人会议只有用户明确“复制为项目纪要”后形成独立快照才可共享，原私人会议不跟随共享；用户直接引用无权查看的私人会议时不返回标题或正文。

## 6. 权限规则

### 6.1 身份与可见性

- HTTP：每次验证有效账号，并查询有效项目成员；不能只信任页面缓存或 Cookie 内的旧角色。
- 私有需求：project_id IS NULL，保留当前作者隔离和既有超管行为。
- 项目需求：按项目成员及动作授权，user_id 仅用于来源追溯。原作者退出项目后不能凭作者身份继续访问。
- 全局超管：保留明确的运维只读可见性；没有项目角色时不能直接执行项目范围、验收、任务确认、结项等业务写入，也不能给自己悄悄加角色。管理自身私人数据的原有能力不变。
- 无账号绑定的旧 MCP：默认只能沿用已定义的私有域行为，对项目列表、共享需求、references、问题、文件、图片、写准备与执行全部默认拒绝；列表过滤，单条不透露存在性。客户端名称、actorName、工具入参 userId 均不是可信账号凭证。
- 系统用途：迁移、种子、定时计时各自明确范围。HTTP 和 MCP 不得落入一个“未提供身份即全库”的共享域后备分支。

### 6.2 角色与操作

角色代码统一为 owner（项目负责人）、product_owner（产品负责人）、contributor（执行成员）、viewer（只读成员），允许兼任。能力按角色求并集；只读成员是“仅有 viewer 角色”的成员。

### 6.3 资源必须整体授权

S1 必须在同一可发布阶段覆盖：需求查询/搜索/references/主子关系/历史、问题和活动、两代文件接口、artifact node/link、内容和 raw 下载、两套图片 URL、记忆、目录、刷新/修复、上传、最终版、本地 open、反查关联和项目统计。

只带 nodeId、linkId、fileId 或 issueId 的请求，先读取最小归属信息，定位真实 requirement_id，再检查项目和动作；不能信任客户端同时传来的 projectId。关联两个资源时，两边都校验且须在允许的同一项目/需求范围内。

## 8. 状态机与交接条件

### 项目

planning（筹备中）→ active（进行中）→ awaiting_acceptance（待验收）→ closed（已结项）；另有 paused（已暂停）、cancelled（已取消）。归档用 archived_at 表示，不增加与业务状态混淆的状态值。

- start：确认项目/产品负责人，目标可逐步补充；不能要求创建时填完全部信息。
- pause/resume/cancel/reopen：记录原因。暂停保存原状态，恢复至原来的 active 或 awaiting_acceptance。
- reopen：适用于 closed/cancelled，明确回到 active；保留原结项/取消结论，已结项重开另追加结项历史，不删除历史验收。
- submit_acceptance：最终承诺范围已确认，有明确验收人和交付证据；中间批次提交验收不强制改整个项目状态。
- close：承诺范围均验收通过或存在经批准的取消/延期/豁免；所有阻断问题已解决或有项目负责人接受风险；每项延期有后续去向，或责任人＋跟进日期；无尚待处理的范围处置。
- 已结项、已取消、已归档默认只读；重开、恢复及解除归档是明确命令。系统不会因归档删除文件或工时。
- 只有已结项或已取消项目可归档；进行中项目先完成明确的结项/取消流程。暂停期间仍可维护说明和计划，执行提交、验收和结项必须先恢复。

### 项目任务

pending → in_progress → pending_confirmation → completed；另有 blocked、cancelled。blocked 记录原状态与原因；恢复回原状态。提交必须有处理说明或产物；退回必须有原因并回 in_progress。已完成任务重开需确认人或有管理能力者填写原因，原确认记录保留。

任务全部完成只给推进提示，不自动改变需求阶段、需求状态、上线或交付验收。今日安排完成也不自动提交项目任务。

### 交付

planning → active → awaiting_acceptance → accepted；另有 cancelled。验收不通过后回 active，下一次提交新增轮次。验收时仍逐项记录；豁免不是通过，验收汇总必须分开显示通过数、豁免数、延期数和未通过数。

需求保留原有五阶段及六状态，不以任务状态替换需求状态。跳过或退回需求阶段必须填写 stageNote，记录真实操作者。已确认范围中的叶子增加子项、删除、改父级、转移或改变验收标准，都属于影响承诺的变更，不可通过通用 PATCH 绕开。

## 9. 指标、风险与待办口径

- 概览统计范围为当前承诺交付范围的有效叶子需求，父需求不重复计数。
- 执行完成：当前范围内 requirement.status=completed 的需求数 / 当前承诺需求数；状态 completed 与 currentStage=online 分开记录，上线不是自动验收。
- 已验收：当前有效验收结论为“通过”的范围项数 / 当前承诺需求数。豁免、延期、取消单列；范围版本变更后不自动继承不再适用的结果。
- 范围未确认/空范围显示“尚未确认范围”，分母及百分比为 null，不能显示 0/0=100%。
- 需求任务数不混入需求完成率。概览不从当前分页的 20 行需求或前端缓存估算全项目指标。
- 风险来源为阻塞需求、逾期未完成项目任务、逾期未验收交付、未通过验收/交付阻断问题；按来源实体去重，返回原因和跳转链接。首版不新增独立风险台账。
- 待我处理按当前账号聚合：待提交/被退回的本人任务、待本人确认任务、待本人验收交付、职责内待处理的范围变更。只计算有动作权限的事项。
- 业务日期按现有业务时区口径；事件时间存 ISO UTC。到期当日不算逾期，从业务日次日开始；已暂停是否继续提示由状态显示解释，不能改写原计划日期。

## 10. 自动保存、冲突与页签

普通字段和正文继续采用 700ms 防抖及失焦保存，明确展示保存中、已保存、失败、冲突。确认范围、任务提交/确认、验收、结项等使用明确按钮，不能自动保存时顺便执行。

1. 每个编辑实体保存 baseVersion、serverSnapshot、localRevision、dirtyPatch 和请求中快照。
2. 同实体请求串行；保存期间输入形成新修订。旧响应只确认已发快照，不能重建整个表单或清除新修订 dirty。
3. 原子 SQL 使用 id + version 条件，自增 version；事务内重新校验成员与动作。成功后返回完整最新版本。
4. 409 暂停该实体自动重试，保留本地草稿，展示服务器新版本。用户可保留/复制草稿、读取最新内容并手动合并；V1 不做富文本自动三方合并，也不静默 force 覆盖。
5. 文件读取返回全文哈希，所有共享正文保存携带 expectedVersion；保留外部磁盘修改校验。force 也不能绕过成员或基准版本校验，用户确认后必须基于最新版本重新提交。
6. 本地输入同步写入按账号/项目/实体隔离的 sessionStorage 草稿，以便同一标签页刷新恢复；不复用只存布局的 tab localStorage。存储失败需提示，不能承诺断电/清缓存后仍可恢复。
7. 路由离开、关闭当前签、关闭后台签、关闭其他/全部、退出登录都经 editing-sessions 统一 flush。失败留在页面或明确选择放弃；批量关闭先校验全部目标，再改变布局，避免半批关闭。
8. KeepAlive 缓存与工作页签生命周期同步；关闭不只是移除签条。权限失效主动取消请求、停止队列并清理预览和相关缓存。
9. 401 暂停发送并保留本账号会话草稿；重新登录同一账号、重新通过项目授权后才恢复。403/404 明确失权后清理该项目缓存与可恢复草稿，不给下一账号看旧内容。
10. 页面激活、窗口重新可见及最长 30 秒周期刷新权限和版本。已经看过/下载过的内容无法远程撤回；失权保证针对后续接口读取/写入。私有图片/下载返回 private/no-store，避免共享缓存继续复用。

先修公共引用解析覆盖输入（BUG-004），再复用编辑器。优化点/便签的其他已知缺陷不应在本功能中整体重写；如复用它们的实现，先移除对应竞态，另在 Bug 表逐项记录。

## 11. 成员移除、停用与责任交接

移除预检列出：主要项目/产品负责人、需求负责人、开发负责人、未完成任务执行人/确认人、进行中交付验收人。修改角色导致所需能力丢失时同样运行预检，例如执行成员降为仅 viewer，必须先移交未完成任务/确认/验收责任，否则返回 RESPONSIBILITY_TRANSFER_REQUIRED。当前 S1 已存在的责任必须全部处理；S2/S3 增加责任类型时同步扩展，不能仅修页面。

移交目标为 active 且具有所需能力的项目成员。S1 先逐需求移交，再修改成员；预检不是锁，正式成员变更在同一写事务中重验全部现有责任，再更新成员/角色、项目 version 和事件。两个并发移除不能移掉最后一位 owner。S2/S3 扩展任务/交付责任时，再增加多对象原子移交命令。已完成历史继续保留原操作者，不为了移交篡改历史。

账号停用立即使其会话失效。停用导致的未完成责任作为项目阻断待办，由其他 owner 移交；不能让停用账号继续确认。若唯一 owner 被运维停用，只能走明确且审计的运维责任移交命令，不能开启任意项目业务权限。
