# superPM 项目管理 V1 产品设计初稿

日期：2026-11-19。更新：2026-11-20。状态：团队协作与概览方向已确认；S0/S1 已实现并通过本阶段验收，S2—S4 尚未实施。实际交付与验证以开发入口为准。

开发入口：[项目管理 V1 开发文档](../plans/2026-11-19-project-management-v1-development.md)，首个执行计划：[S0.1 共享项目契约](../plans/2026-11-19-project-management-s0-contracts.md)。本稿保留产品意图，开发约束和进度以开发入口为准。

用户已确认：团队协作，项目经理、产品经理、开发使用各自账号，共同推进同一个项目。

## 1. 定位与方案选择

把项目作为业务交付容器，承接目标、范围、责任和验收；需求继续承担产品定义，项目任务承担研发执行。一个人也能创建项目、兼任多个角色，但不能以个人账号的数据归属代替项目权限。

| 方向                           | 优点                                                 | 不足                                         | 结论               |
| ------------------------------ | ---------------------------------------------------- | -------------------------------------------- | ------------------ |
| 轻量项目＋需求＋执行＋交付验收 | 有完整交付主线，能够复用已有能力，项目信息可渐进补充 | 需要新增项目协作权限和交付记录               | 推荐               |
| 只给需求增加项目分类           | 开发量小、上手快                                     | 没有范围承诺、责任交接和验收，不构成交付闭环 | 不作为本期目标     |
| 完整企业项目管理平台           | 可覆盖合同、预算、资源等管理事项                     | 初期维护负担大，偏离产品经理日常             | 后续按实际需要扩展 |

初版应能回答：为什么做、做哪些、谁负责、做到哪里、何时交付、谁确认交付。

## 2. 核心对象与边界

| 对象     | 承担职责                                           | 与已有功能的关系                             |
| -------- | -------------------------------------------------- | -------------------------------------------- |
| 项目     | 客户／业务背景、目标、范围、负责人、成员、整体交付 | 新增在需求之上的组织层                       |
| 需求     | 业务目标、需求说明、验收标准、分析到上线的阶段跟踪 | 保留现有两级主子需求、阶段、问题、文档与产物 |
| 项目任务 | 可跨日指派的设计、开发、测试、部署等具体工作       | 新增；不直接把个人每日任务变成共享任务       |
| 交付批次 | 约定本次交付范围、计划日期、交付证据和验收结论     | 默认提供一次交付；需要分期时再增加批次       |
| 每日任务 | 个人今天的安排与计时                               | 可引用项目任务；私人日程继续保持私人         |

主线：项目目标 → 需求确认 → 任务执行 → 测试／上线 → 交付验收 → 项目结项。验收失败进入问题处理后再验收；新增范围进入变更需求，再安排批次。

交付批次是需求的交付分组，不新增“项目—阶段—子项目—迭代”等多重强制层级。项目自带默认交付范围及验收入口，不因用户未手建批次而断环。

## 3. 项目信息保持轻量

### 创建时

唯一必须手填的是项目名称。系统自动生成项目编号，例如 PRJ-0001，负责人默认创建人，状态默认“筹备中”，产品负责人默认同一人。成员可后续添加。

### 按推进阶段逐步补齐

| 信息                       | 创建时             | 正式推进／交付时         |
| -------------------------- | ------------------ | ------------------------ |
| 项目名称                   | 必填               | 可改名，保留历史         |
| 项目目标、范围摘要         | 可稍后填写         | 首次确认交付范围前必填   |
| 项目负责人、产品负责人     | 默认创建人，可兼任 | 必须明确                 |
| 客户／业务方、联系人       | 选填               | 内部产品可以一直不填     |
| 计划开始、目标交付日       | 选填               | 确认交付范围时明确交付日 |
| 项目成员与责任分工         | 可稍后添加         | 指派任务时必须是有效成员 |
| 本次范围、验收标准、验收人 | 可稍后确认         | 提交验收前明确           |
| 合同、预算、回款、采购等   | 不设置必填入口     | 不纳入本期               |

默认页面突出目标、交付日、进度和风险。客户背景等放在可折叠的“项目信息”中，不要求产品经理先填写完整项目档案才能记录需求。

## 4. 成员与责任

角色按项目分配，同一个人在不同项目中可有不同角色，也可兼任。

| 角色       | 初版主要能力                                                             |
| ---------- | ------------------------------------------------------------------------ |
| 项目负责人 | 维护项目、管理成员、确认计划和范围变更、处理例外、结项及重新开启         |
| 产品负责人 | 维护需求与验收标准、组织需求确认、推进需求阶段、确认交付验收             |
| 执行成员   | 开发／测试／设计参与者，领取或接受任务、更新执行进展、提交产物及验证结果 |
| 只读成员   | 查看项目内允许共享的需求、任务、进度和交付资料                           |

每个需求有一名主负责人，可另设开发负责人；每个任务有一名执行负责人及一名确认人，确认人默认需求负责人，未关联需求的项目级任务默认项目负责人。验收人默认产品负责人，可指定其他项目成员。角色可兼任，但操作记录必须保存实际操作者。

执行成员可更新分配给自己的任务、补充问题与产物，不能自行改动已确认交付范围、他人任务负责人或完成项目结项。项目负责人管理项目级任务；产品负责人管理需求下任务，并可指定需求开发负责人，由其拆分和指派该需求内任务，但不能变更交付范围。不得移除最后一名项目负责人。

初版从本系统已有账号添加成员，不做企业组织架构、邮件邀请、客户外部账号或自定义权限矩阵。客户验收意见可由内部验收人录入并附证据，记录应区分系统操作者与客户确认人。

## 5. 页面结构

左侧导航在“需求列表”上方新增“项目管理”。保留全局需求入口，并增加项目筛选及“未归项目”，不强制用户必须先进入项目才能搜索需求。

### 项目列表

- 搜索和筛选与“新建项目”按钮放在同一工具栏，默认列表展示。
- 主要列：编号、名称、客户／业务方、负责人、状态、目标交付日、已验收／承诺范围数、风险。
- 支持“我负责的／我参与的／已归档”筛选；只展示有权限的项目。
- 风险提示优先来自现有阻塞需求、逾期任务、逾期交付和未通过验收，不另建一套复杂风险台账。

### 项目详情

顶部固定显示名称、状态、负责人、目标交付日和成员入口。一级页签建议为：概览、需求、任务、交付、资料、动态。

| 页签 | 核心内容                                                                               |
| ---- | -------------------------------------------------------------------------------------- |
| 概览 | 项目目标；当前交付范围；需求阶段分布；逾期／阻塞；最近变动；待我处理事项               |
| 需求 | 复用现有需求表格、主子结构、排序、置顶和详情，增加负责人、所属批次与验收标准入口       |
| 任务 | 列表为默认视图，支持“分配给我”、负责人、状态、需求筛选；简易看板作为同一数据的可选视图 |
| 交付 | 默认交付或多批次的范围、计划、发布说明、交付证据、验收结果                             |
| 资料 | 项目级资料、会议与决策入口，以及需求产物的聚合引用；不重复复制需求文件                 |
| 动态 | 成员、范围、负责人、状态、交付及验收变化，可追溯操作者与时间                           |

## 6. 从目标到验收的最小闭环

| 环节     | 负责人           | 输入／动作                                           | 交接结果                   |
| -------- | ---------------- | ---------------------------------------------------- | -------------------------- |
| 项目筹备 | 项目负责人       | 写明业务目标，添加成员，约定交付时间                 | 团队知道为什么做、谁负责   |
| 需求确认 | 产品负责人       | 整理需求说明与验收标准，明确纳入本次的需求           | 明确本次范围及确认版本     |
| 工作拆分 | 产品／开发负责人 | 按需拆设计、前后端、联调、测试任务，指派负责人和日期 | 开发知道具体工作与完成标准 |
| 执行跟进 | 任务负责人       | 更新状态、阻塞原因、产物或代码链接                   | 提交可验证的结果           |
| 验证上线 | 确认人／测试人员 | 验证任务和需求，问题关联原需求，记录上线时间与证据   | 功能可交付，遗留问题有处置 |
| 交付验收 | 指定验收人       | 对照约定范围和标准逐项确认，记录结论与证据           | 已通过或退回处理，保留历史 |
| 项目结项 | 项目负责人       | 核对承诺范围与遗留事项，填写结项结论                 | 形成完整可追溯交付记录     |

需求可以不拆研发任务，避免简单需求也被迫创建多条工作项；仍须明确负责人和验收标准。项目任务可直接归项目处理部署等工作，研发任务则关联一个叶子需求。任务类型不强制全部创建。

## 7. 状态和交接规则

### 项目

主流程：筹备中 → 进行中 → 待验收 → 已结项。另有已暂停、已取消；恢复或取消须记录原因。多批次项目在中间批次验收时可保持进行中，最终承诺范围准备验收时才进入项目待验收。已结项默认只读，由项目负责人填写原因后重新开启。归档只是收起历史项目，不删除需求或文件。

### 项目任务

待开始 → 进行中 → 待确认 → 已完成；可进入阻塞或已取消。执行人提交完成说明／产物后进入待确认，由确认人通过或退回。无需产物的任务可填写处理说明。同一人兼任时允许自确认，仍保留动作记录。

任务全部完成只提示“可推进需求”，不自动把需求改为已完成或已上线；今日安排完成也不自动完成项目任务。

### 需求

保留当前状态与需求分析、UI 设计、开发跟进、需求测试、已上线五个阶段。需求说明、问题和产物继续在现有详情中维护，不新建第二份 PRD。简单需求可跳过不适用阶段，但记录原因和操作者。

### 交付与验收

批次状态：计划中 → 进行中 → 待验收 → 已验收，另可取消。提交验收时记录交付版本、实际交付日期和证据，逐项保存通过／不通过／豁免结果。未通过项必须记录原因并关联问题，返回处理中后可再次提交；每次验收记录追加保留。

产品负责人或项目负责人可将问题标记为“阻断本次交付”，必须注明影响。结项条件是承诺范围已验收，或已逐项批准取消、延期、豁免且有原因和后续去向；阻断问题必须解决或由项目负责人明确接受风险并留痕。任务完成、需求上线均不能自动替代交付验收。项目有多批次时，单批通过也不自动结项。

## 8. 范围、进度和变更

1. 一条需求最多属于一个项目；主子需求树同属一个项目，不能把子需求挂到其他项目。
2. 交付范围按叶子需求选择和统计，父需求只负责分组，防止主子需求重复计数。同一叶子需求最多属于一个进行中的交付批次。
3. 确认交付范围时保存需求及验收标准的版本和确认人；新增、移出、延期需求都须填写原因并保存范围版本。已纳入范围的需求增删子项同样按范围变更处理，不允许静默改动统计分母。
4. 概览分开展示“执行完成 X/Y”和“已验收 X/Y”；前者按需求执行状态，后者按交付验收结果，任务数量不混入需求完成率。
5. 未确认范围或范围为空时显示“尚未确认范围”，不显示 100%。豁免／延期单独显示，不能混作已验收通过。
6. 已验收需求出现新业务范围时，优先新建关联的变更需求并安排新批次；修复未满足原验收标准的问题则回到原问题记录。历史验收快照不被新正文覆盖。
7. 项目结项只检查最终约定范围，不要求将未承诺的产品储备需求全部做完；延期必须有后续项目／批次去向或明确记录待定责任人及跟进日期。

## 9. 与个人每日任务衔接

项目任务可以跨多天，当前每日任务以日期组织且有单日工时限制，因此两者不合并为一张任务清单。

- 在项目任务上选择“安排到我的今天”，每日任务引用该工作项，可设置今日计划时段与预计耗时。
- 同一项目任务可对应多天的个人安排，项目工时仅汇总这些明确关联的工时记录，一条工时只计一次。
- 个人每日安排完成代表当天计划结束，项目任务是否提交确认由执行人明确操作。
- 已关联项目的工时在安排时提示将按项目权限汇总；未关联的个人任务、便签和日程不进入项目共享范围。
- 初版项目内任务页提供“分配给我”和待确认筛选，不额外强制新增一套全局工作台；消息先提供站内待办，不做邮件、短信或外部平台推送。

## 10. 保存与并发编辑

普通字段、说明正文沿用轻量编辑体验，防抖及失焦保存，并明确显示保存中、已保存、失败、存在未保存修改。确认范围、提交验收、接受豁免、结项等业务动作使用明确按钮。

所有共享对象更新携带版本。旧版本提交时保留本地草稿并提示冲突，不静默覆盖他人修改。保存请求期间的新输入必须保留为新修订；失败时保留草稿并提供重试，离开前等待保存，失败则拦截或由用户明确放弃。

## 11. 存量与权限边界

- 历史需求默认仍是原有私有、未归项目的数据，不自动对任何新项目成员共享。
- 将私人需求加入项目必须明确确认共享范围；主子需求、问题、历史和需求产物一并按项目权限处理。私人便签和个人日程不随之共享。
- 原作者身份保留用于追溯，不作为绕过成员权限的永久通行证；离开项目后失去项目数据访问权。移除成员前必须重新指派其未完成责任，历史记录保留。
- 需求、文件、图片、问题和下载接口均须校验真实项目成员权限，不能只隐藏菜单，也不能通过取消原有过滤或让成员使用超管账号实现共享。
- 初版不开放跨项目直接移动有历史的需求；需要调整时复制形成新需求并保留来源。加入项目不移动现有需求物理目录，不改需求编号和链接。
- 私人需求加入项目也会使相关条目从个人隔离转为项目访问规则；UI 必须明确提示。项目归档不级联删除需求、任务、工时或文件。
- 项目多人协作使用同一个服务实例及数据库。不同电脑各自安装的独立实例不会自动同步；共享实例部署需另行确认，不在本次设计中自动修改监听地址或开放网络。
- 新项目 MCP 工具后续接入时必须带明确用户／服务账号身份和项目权限；不直接沿用无身份的全库访问。初版不以扩展 MCP 写权限作为协作前提。

## 12. V1 范围与实施分批

以下保留产品能力分批；对应的实施顺序、技术约定和验收关口已整理到上方开发文档。

第一批：项目列表与详情、成员和基础角色、需求归属／负责人、全局筛选、旧数据兼容和项目权限。目标是团队在同一项目中安全共用需求与资料。

第二批：跨日项目任务、个人今日安排关联、默认交付／分批交付、范围确认与变更、验收记录、结项检查及概览聚合。目标是将执行和交付闭环跑通。两批合起来构成本设计的 V1，第一批不能宣称完整交付闭环已经完成。

后续再考虑：产品／组件维度、多项目共用能力库、完整测试用例与执行、甘特依赖和资源负载、Git／CI／外部缺陷平台自动关联、客户门户、复杂审批、自定义字段、预算合同回款。

## 13. 最低验收场景

1. 项目经理创建项目并添加产品、开发账号，各账号只看到已加入的项目；私人旧需求仍不可见。
2. 产品负责人将需求加入项目，确认共享，再明确负责人、验收标准及本次范围；子需求不产生跨项目归属。
3. 开发看到分配给自己的跨日任务，分两天安排工作与计时，不出现重复任务完成率或重复工时。
4. 开发提交产物，确认人退回后可重新提交；研发任务全部完成不会自动完成需求或验收。
5. 一次验收不通过，关联问题处理后再次通过，前后两次结果和证据均可追溯。
6. 不新增批次也能完成默认交付；多批次只完成一批时项目不能被自动结项。
7. 范围变更、取消、延期、豁免有原因，叶子统计不重复，历史验收不会因改正文被覆盖。
8. 同时编辑发生版本冲突或网络保存失败时，草稿不丢失，不能无提示覆盖他人修改。
9. 成员退出或被移除后，仍不能通过旧 URL、附件、图片或下载链接访问项目内容。
