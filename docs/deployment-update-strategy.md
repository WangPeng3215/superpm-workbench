## 1. 设计目标

建立适用于个人本地部署的低成本版本更新机制，支持从应用内检查更新、查看更新说明、下载更新包并完成安装。

设计原则：

- 无需自建更新服务器，优先使用现有代码托管平台提供的版本发布能力。
- 源码、应用程序、用户数据相互分离，更新程序不得覆盖用户数据。
- 更新过程具备备份、校验、迁移、验证和失败恢复能力。
- 更新操作尽量自动化，减少手动替换文件、复制数据和重新配置环境的工作。
- 优先保证数据安全和更新可靠性，再逐步完善自动更新体验。

## 2. 更新架构

更新机制由以下部分组成：

1. **Git 源码仓库**：管理源码、开发记录和版本标签。
2. **发布构建流程**：构建前端静态文件、后端程序及其他必要运行文件，生成正式发布包。
3. **版本发布源**：存放版本清单、更新说明和安装包。优先使用现有托管服务，不单独搭建更新服务器。
4. **应用内更新页面**：负责检查版本、展示更新说明、下载更新包和显示安装状态。
5. **独立更新执行器**：负责停止应用、备份数据、替换程序、执行数据库迁移、重启验证及失败恢复。
6. **本地数据存储**：保存 SQLite 数据库、需求文件、图片、配置和其他用户产出物。

应用内页面不得直接覆盖正在运行的后端程序。涉及程序文件替换时，应由独立更新进程执行。

## 3. 程序与用户数据隔离

发布包通过 `SUPERPM_HOME` 或配置指针将数据库与用户文件放在独立数据根，Windows 默认 `%LOCALAPPDATA%\superPM`，也可显式覆盖。安装目录仅保留 `SuperPM.cmd`、`Stop.cmd`、`Stop.ps1`、`Update.cmd`、`bin/`、`runtime/` 与可替换的 `app/`；M1 已实现安装目录旧数据的一次性迁移、备份与恢复验证，后续更新只替换 `app/`，不再迁移数据。开发环境不设置 `SUPERPM_HOME`，仍沿用仓库内 `data/` 与 `workspace/`。

0.4.0 起，发布版可在「系统设置 → 本地存储」更换保存位置。所选数据根写入配置目录 `%APPDATA%\superPM\config.json`（`SUPERPM_CONFIG_DIR` 仅供测试/演练覆盖），优先级为 `SUPERPM_HOME` > 配置指针 > 平台默认目录。启动保护要求配置指针指向的目录已存在且包含数据库或数据根标记，避免移动硬盘或网络盘未挂载时静默新建空库；需要恢复默认目录时，停止应用后把 `config.json` 改名即可。

数据保护要求：

- SQLite 数据库、需求文件、问题记录、需求记忆、图片及其他用户产出物必须受到保护。
- 用户配置、必要的本地运行配置和密钥不得被新版本默认覆盖。
- 发布包只包含运行程序及必要资源，不得包含开发者本机数据库、真实用户数据、个人配置或密钥。
- 更新程序只能替换明确列入更新清单的应用文件。
- 数据目录迁移必须具备备份、迁移验证和失败恢复能力。
- 未完成数据隔离与恢复验证前，不得启用正式在线更新。

实际目录结构以项目现有代码和部署方式为准，不得直接套用示例路径。

## 4. 版本检查机制

应用内「系统设置 → 版本与更新」入口已由 M3 提供；`Update.cmd --manifest <清单地址>` 仍作为页面不可用或离线场景的命令行入口，执行相同的清单读取、版本比较、下载与安装流程。

用户点击「检查更新」的流程为：

1. 获取当前安装版本。
2. 请求配置的版本发布源。
3. 读取最新正式版本的版本清单。
4. 比较本地版本与最新版本。
5. 展示检查结果、更新说明及安装提示。

检查结果包括：

- 当前已是最新版本。
- 发现新版本，可查看更新说明并选择安装。
- 检查失败，提示网络异常、发布源不可用或清单校验失败等原因。

检查更新失败不得影响当前版本的正常运行。

M3 的实际检查行为：

- 由服务端读取清单，避免浏览器直连发布源；接口要求登录会话。
- 仅接受 HTTPS 与内置主机允许列表，手动校验每一跳重定向，拒绝携带账号信息或非 443 端口的地址；清单上限 1 MiB。
- 清单必须匹配产品名、平台与当前 schema 下限，并校验最低更新器版本。
- 有效清单缓存到数据根 `updates/available-manifest.json`；安装时必须与缓存版本一致，避免检查后发布源变化导致安装非预期版本。
- 开发环境允许检查，但安装返回不支持原因，仍使用命令行更新或完整安装包。

## 5. 版本发布与更新包

每次正式发布应包含：

- 唯一版本号。
- 发布日期及更新说明。
- 可下载的完整安装包。
- 安装包 SHA-256 摘要。
- 数据库迁移版本要求及相关迁移脚本。
- 必要的最低更新器版本要求。

版本号遵循项目的《版本号管理规范》。

M2 发布脚本 `scripts/release/build-release.mjs` 会生成完整安装包、仅含 `app/` 的增量更新包和 `update-manifest.json`。清单字段包括 `manifestVersion`、`name`、`version`、`platform`、`releasedAt`、`schemaVersion`、`minUpdaterVersion`、`notes`，以及完整包与增量包的 `file`、`url`、`sha256`、`size`。

0.4.0 的 `install.json`、清单 `minUpdaterVersion` 与诊断接口更新器版本统一为 `1.1.0`。0.3.3 自带的 1.0.0 更新器只接受仅含 `app/` 的增量包，不能替换 `bin/`，因此 0.4.0 必须通过完整安装包覆盖安装一次（或解压到新目录并更新 MCP 启动路径）；应用内检查到 0.4.0 会因最低更新器版本不足而拒绝，这是预期行为。完成这次 bootstrap 后，后续版本恢复增量更新。

版本清单中的下载地址、文件摘要和版本信息必须与实际发布产物一致。更新源应使用 HTTPS，并限制为受信任的来源。更新器只允许清单与更新包来自内置 HTTPS 主机允许列表。

SHA-256 用于校验文件完整性；如果需要防范发布清单被篡改，应进一步引入数字签名校验。数字签名不在 M2 范围内。

## 6. 更新安装流程

用户在应用内确认安装后，按照以下流程执行：

1. **准备更新**：检查安装包、目标版本、磁盘空间、更新器版本及兼容性。
2. **下载更新包**：下载至临时目录，不直接修改当前运行文件。
3. **校验更新包**：校验 SHA-256、版本信息和安装包结构。
4. **停止应用**：停止后端及相关进程，确保 SQLite 不再有未完成写入。
5. **备份数据**：备份 SQLite 数据库、必要配置及更新所需保护的数据。
6. **保存旧版本**：保留当前应用文件，以便失败时恢复。
7. **安装新版本**：替换明确允许更新的应用文件。
8. **执行数据库迁移**：按照顺序执行尚未执行的迁移脚本，并记录迁移状态。
9. **启动并验证**：重新启动应用，检查后端健康状态、数据库访问和关键业务功能。
10. **完成更新**：验证通过后记录新版本号，保留必要的恢复备份。
11. **失败恢复**：恢复旧程序和升级前数据库，重新启动旧版本并记录错误日志。

更新执行器必须独立于正在被替换的程序，避免 Windows 文件占用导致安装失败。M2 的更新器启动后先把自身复制到系统临时目录再执行；原 `app/` 改名为 `app.previous` 完成回退准备，成功后保留该目录。

M2 的实际行为补充：

- 更新器接受 HTTPS 清单/安装包，也接受本地清单与更新包用于离线演练；HTTPS 主机必须在允许列表内。
- 解包只接受全部位于 `app/` 下的条目，拒绝绝对路径、盘符、`..`、符号链接与超限解压；包内 `package.json` 版本和 schema 必须与清单一致。
- schema 不允许降级；目标版本必须高于当前版本。
- 服务未运行时，更新器从数据根 `.env`、安装目录 `.env` 或 `PORT` 解析端口，更新后沿用同一端口。
- 替换程序前失败时，旧程序保持不变，更新器自动重新启动旧版本；替换或迁移后失败时，恢复旧程序、更新前数据库、工作区与 `.env` 并启动旧版本。
- 回滚失败时保留更新锁，阻止继续启动；用户需按 [`install-update.md`](install-update.md) 手动恢复。
- 更新结果写入数据根 `updates/last-update.json` 与 `logs/update.log`。

### M3 应用内下载与安装

应用内安装沿用同一套独立更新器，服务端只负责检查、下载与转交：

- 安装前校验缓存清单版本、目标版本高于当前版本、平台/schema/最低更新器版本，并检查更新锁与存活 MCP 进程；MCP 未关闭时必须显式强制。
- 服务端将更新包下载到 `updates/downloads/<版本>/update.zip`，边下载边计算 SHA-256 并反馈百分比；校验大小与摘要失败时删除文件，不启动更新器。
- 校验通过后生成 `updates/install-manifest.json`，更新包地址改为本地文件 URL，再以数据根运行时启动 `bin/updater.mjs --manifest ... --install-root ... --home ... [--force]`。更新器重新校验摘要与结构后才替换程序。
- 更新器把阶段、百分比与错误写入 `updates/update-progress.json`；页面轮询 `/api/update/status`，服务重启期间按离线重试，成功后在版本号确认与 `last-update.json` 基础上刷新页面。
- 旧版更新器未写入进度文件时，页面以新版本号与最近一次更新结果作为兜底判断。

### 数据根在线迁移（0.4.0）

- 设置页只向服务端提交父目录；服务端统一解析为 `<父目录>\superPM`（父目录名已是 `superPM` 时直接使用）并完成绝对路径、嵌套关系、可写、空间、数据库完整性与工作区数量校验。
- 确认后服务端写入迁移任务、状态与 `operation.lock`，启动独立的 `bin/move-home.mjs`。迁移助手停止 HTTP 服务，使用 SQLite 在线备份，复制数据、工作区、`.env` 与备份到目标卷的暂存目录，校验表行数与文件清单后原子切换。
- 切换后写入目标数据根标记、旧数据根迁移标记与配置指针（含 `previousHome`），启动新服务并等待健康检查通过；失败时恢复旧配置并重启旧数据根，状态与日志保留。
- 旧数据默认保留；用户在设置页选择保留或删除。删除接口同时校验任务 ID、旧数据根、当前数据根、旧目录标记与允许的相对路径，只处理 `data`、`workspace`、`backups`、`.env`，不跟随符号链接。
- 迁移与更新共用操作锁：迁移期间启动器、更新器与 MCP 均拒绝启动；更新或 MCP 存活时迁移也拒绝开始。
- 状态写入配置目录 `move-home.json`，日志写入 `logs/move-home-<日期>.log`；页面轮询迁移状态，服务重启期间按退避重试并在恢复后继续展示进度或结果。

### MCP 连接检测与强制中断

MCP 由各客户端拉起独立的 stdio 进程，即使客户端空闲，进程仍持有程序文件和数据库连接。更新期间必须显式处理：

- MCP 进程启动时在数据根 `runtime/` 注册 PID 并定期写入心跳，正常退出时注销。
- 检测到存活 MCP 进程时，默认阻止安装，并列出进程与所属客户端，提示关闭客户端后重试。
- 用户可显式选择强制更新，流程分两级：
  1. **优雅退出**：写入更新锁，MCP 在心跳周期内发现退出请求，关闭数据库、注销 PID 后退出；最多等待 15 秒。
  2. **强制结束**：超时后经用户二次确认，终止残余 MCP 进程，再继续备份与替换。
- 更新锁存在期间，新启动的 MCP 进程必须拒绝连接，避免客户端自动重连拉起旧代码与新数据库混用。
- 数据库备份与完整性校验通过后才替换程序；失败则恢复旧程序与升级前数据库并释放更新锁。

强制更新的已知影响：

- 正在执行的 MCP 工具调用会失败，调用方需要重试。
- 客户端会显示服务断开；更新完成后 MCP 进程由客户端重新拉起，部分客户端需要重启或手动重连才能恢复，工具列表也要重连后刷新。
- 未提交事务回滚；已提交数据保存在 WAL 中并包含在备份内。极端文件系统异常下仍有损坏可能，因此必须保留备份与回滚能力。
- 更新窗口内 MCP 不可用，客户端自动重连会因更新锁短暂失败。

## 7. 数据库迁移规则

数据库结构升级必须使用可追踪、按顺序执行的迁移机制。

- 独立记录数据库当前版本。
- 每次迁移具有唯一编号，避免重复执行。
- 执行迁移前完成数据库备份。
- 迁移失败时停止后续安装流程。
- 不得通过删除旧数据库并重新建库的方式完成升级。
- 数据库迁移完成后，应验证关键表、关键数据和必要的业务读写能力。
- 回滚时必须恢复与旧程序兼容的数据库状态，不能只恢复程序文件。

数据库结构变更不自动触发主版本升级，但每次发布都必须明确其数据兼容性和迁移要求。

## 8. 更新失败与恢复策略

以下情况均应进入失败处理流程：

- 下载中断或安装包校验失败。
- 磁盘空间不足。
- 应用进程无法正常停止。
- 程序文件替换失败。
- 数据库迁移失败。
- 新版本启动失败或健康检查不通过。

失败处理要求：

- 不得将失败的更新标记为成功。
- 保留失败阶段、错误原因和日志。
- 替换程序前失败时保持旧程序不变，并恢复旧版本服务；替换后失败时尽可能恢复旧程序及升级前数据库。
- 恢复失败时保留所有可用备份，不得自动删除用户数据。
- 不得在恢复状态未确认前清理旧版本和数据备份。
- 必要时提示用户手动恢复，并明确给出备份和日志位置。

M2 使用三种结果状态：`failed`（替换前失败，旧版本保持或恢复运行）、`rolled-back`（替换后失败，旧程序与更新前数据已恢复）、`rollback-failed`（回滚失败，更新锁保留，必须手动处理）。

## 9. 发布管理规则

- 每个正式发布版本对应唯一 Git 标签，例如 `v0.3.0`。
- Git 标签、应用内版本号、发布清单和安装包版本必须一致。
- 同一正式版本号不得被其他构建产物覆盖。
- 发布前完成基本功能验证。
- 涉及数据库变更时，必须验证升级和失败恢复流程。
- 发布包应排除开发环境文件、临时文件、真实用户数据、密钥和不必要的开发依赖。
- 更新日志应记录版本号、发布日期、变更内容、数据库迁移要求及已知问题。

## 10. 分阶段实施计划

### 阶段一：现状审查与数据保护（已完成）

- 确认前端、后端和 MCP 的启动方式。
- 确认现有打包命令及部署目录结构。
- 确认 SQLite 数据库、用户文件和配置的真实路径。
- 梳理现有数据库初始化及迁移逻辑。
- 建立数据备份、数据隔离和恢复方案。

### 阶段二：基础更新能力（已完成）

- 统一应用版本号管理（已随阶段一完成）。
- 自带 Node 22 运行时、固定安装布局与稳定启动器。
- 生成完整安装包、增量更新包、版本清单与摘要。
- 实现独立更新执行器：HTTPS 允许列表、摘要/结构校验、停机、更新前备份、程序替换、数据库迁移、健康检查与失败回滚。
- MCP 运行时注册、心跳、更新锁与强制退出。
- 使用 v0.1.0 → v0.2.0 真实产物完成升级演练，并注入下载、校验、备份、替换、迁移与健康检查失败验证回滚。

### 阶段三：应用内检查更新（已完成）

- 系统设置增加「版本与更新」页面，展示当前版本、更新器版本、更新锁与 MCP 进程状态。
- 服务端读取并缓存版本清单，完成语义化版本比较、平台/schema/最低更新器版本校验与下载地址白名单校验。
- 展示更新说明、发布日期、更新包大小与阻断原因，提供安装确认与 MCP 强制更新二次确认。
- 服务端下载更新包并实时反馈百分比，校验 SHA-256 与大小后生成本地清单。
- 调用独立更新器完成停机、备份、替换、迁移、健康检查与失败回滚；更新器写入阶段进度，页面在服务重启后恢复状态。
- 使用真实安装包与更新包完成应用内链路演练：检查与缓存、下载进度、摘要校验、本地清单转交、更新器启动、服务离线重启与进度恢复。

### 阶段四：完善发布流程

- 规范正式版本发布步骤（GitHub Actions 发布标签已建立，待首次正式发布验证）。
- 增加数字签名校验、保留多个恢复点等增强能力。
- 更新器自升级能力评估。
- 根据实际使用情况优化更新体验。

### 阶段五：可配置数据保存位置（已完成，0.4.0）

- 发布包默认数据根保持不变；新增配置指针、来源标记与启动保护，支持在应用内更换保存位置。
- 设置页展示当前数据根、来源、数据库与工作区位置，提供「在资源管理器中打开」与「修改保存位置」；不可编辑时显示具体原因。
- 目标校验覆盖绝对路径、UNC、子目录规则、非空目录、嵌套关系、权限、空间、数据库完整性与数据/工作区重叠。
- 独立迁移助手完成停服、SQLite 备份、复制校验、原子切换、配置指针写入、重启与失败回滚；更新器版本升至 1.1.0。
- 迁移后由用户决定保留或删除旧数据；删除需二次确认并校验任务与目录标记。
- 使用真实发布包完成正向、反向、保留后再次迁移演练，以及 0.3.3 → 0.4.0 完整包 bootstrap 演练。

## 11. 实施约束

- 开发前必须审查现有代码和部署结构，不得假设当前项目的目录、框架或打包方式。
- 未确认数据路径前，不得直接移动或覆盖数据库和用户文件。
- 未完成备份和恢复验证前，不得启用正式在线更新。
- 更新器、数据库迁移和文件替换逻辑必须有明确的失败处理。
- 第一阶段优先实现安全、可验证的更新流程，不追求复杂的自动更新平台。
- 所有更新机制应以本地部署可靠性和用户数据安全为最高优先级。
