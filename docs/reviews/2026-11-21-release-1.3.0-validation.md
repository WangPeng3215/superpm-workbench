## 旧完整包与实际修复包升级演练

旧包由官方 v1.2.0 Release 下载，其 SHA-256 精确匹配 `52bd92c89d8eb23c3796a717eafa36643727c66cc951687b4a4ef5ec2c9a1c4b`。使用本次真实清单、增量包和修复 ZIP，默认八场景全部通过，进程退出码 0。原始结果见 [update-rehearsal.json](../../outputs/reviews/2026-11-21-release-1.3.0/update-rehearsal.json)。

| 场景                                       | 实际结果                                                            | 运行版本 |
| ------------------------------------------ | ------------------------------------------------------------------- | -------- |
| happy                                      | `updated`，MCP 优雅退出，备份、业务数据、工作区、更新状态及进度正确 | 1.3.0    |
| digest / download / verify / backup / swap | `failed`，程序与数据保持，旧服务正常运行                            | 1.2.0    |

每个场景先使用原更新器，确认因最低 `1.1.3` 要求被拒绝，并校验数据库/WAL、原服务 PID/健康、程序和工作区标记不变、更新锁释放；随后仅在临时安装中替换真实修复 ZIP 的更新器，保留原 `install.json` 字节，再执行原升级/回滚断言。成功夹具目录已清理。

## 发布与实际数据边界

本轮使用系统临时目录、专用数据库与自行创建的服务进程，没有更新用户实际安装、迁移真实业务数据或修改个人原型。项目数据和权限的功能证据见 [S3/S4 验证](2026-11-21-project-management-s4-validation.md)，六项缺陷及首轮未再复现的单测异常见 [缺陷验证](2026-11-21-bug-backlog-validation.md)。该异常根因未确认，不因后续通过而声称已解释。

发布使用仓库既有流程：提交并推送当前分支及注释标签 `v1.3.0`，由 `Release` 工作流重新安装依赖、检查类型、运行单测、构建和执行安装冒烟后发布五项资产。此文件记录的是发布前证据；远端是否发布成功以该标签对应的工作流和 Release 资产为准。CI 会重新构建，正式下载文件的摘要以正式清单为准。
