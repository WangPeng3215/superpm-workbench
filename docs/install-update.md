# 安装、更新与回滚

面向使用发布包部署的 Windows x64 环境。开发环境运行方式见根目录 `README.md`。

## 1. 安装包结构

```text
superpm-workbench-<version>-win-x64/
  SuperPM.cmd              启动入口
  Stop.cmd                 停止入口（调用 Stop.ps1）
  Stop.ps1                 停止脚本
  Update.cmd               更新入口
  bin/launcher.mjs         稳定启动器
  bin/updater.mjs          独立更新器
  bin/move-home.mjs        数据根迁移助手
  runtime/node.exe         自带 Node 22 运行时
  runtime/LICENSE          Node 许可证
  app/                     可替换程序目录（不保存用户数据）
  install.json             安装版本、schema 与更新器版本（当前 1.1.0）
  README.txt
```

`app/` 是更新器唯一替换的目录。数据库、工作区、日志和备份均在独立数据根中，不随程序更新变化。

## 2. 首次安装

1. 解压完整安装包到当前用户可写的目录，例如 `D:\Apps\superPM`。不要放进需要管理员权限才能写入的目录，否则更新无法替换 `app/`。
2. 双击 `SuperPM.cmd`。启动器直接使用 `runtime\node.exe`，不依赖系统 Node。
3. 打开 <http://127.0.0.1:3001>，默认账号 `admin`，密码 `admin123`，首次登录后立即修改。
4. 停止服务：在启动窗口按 `Ctrl+C`，或双击 `Stop.cmd`。更新或迁移后服务可能由独立进程静默启动，此时没有前台窗口，请使用 `Stop.cmd`。

数据根默认位于 `%LOCALAPPDATA%\superPM`：

```text
data/          SQLite 数据库
workspace/     需求文件、图片与产出物
logs/          server-*.log、mcp.log、migration.log、update.log
backups/       备份
runtime/       server.json、mcp/、update.lock
updates/       清单缓存、更新包暂存、update-progress.json 与 last-update.json
.env           可选的端口与数据目录配置
```

设置 `SUPERPM_HOME` 可改用其他数据根。安装目录内的旧 `data/`、`workspace/` 与 `.env` 会在首次启动时复制到数据根，校验后落位；旧文件保留不删除。

不设置 `SUPERPM_HOME` 时，发布版从 `%APPDATA%\superPM\config.json` 读取所选数据根，不存在时使用默认目录。该配置指针由「修改保存位置」写入，同时保留上一份为 `config.json.bak`。若指针指向的目录被移动、卸载或为空，启动器会拒绝启动并提示检查磁盘或把 `config.json` 改名以恢复默认目录，避免在空挂载点静默新建空库。`SUPERPM_CONFIG_DIR` 只用于测试或发布演练覆盖配置目录，日常部署不要设置。

常用检查：

```powershell
SuperPM.cmd --version
SuperPM.cmd --home
```

### 停止服务

更新或迁移完成后服务可能由独立进程静默启动，没有保持前台窗口。双击安装目录中的 `Stop.cmd`，或在命令行执行：

```powershell
Stop.cmd                        # 使用当前配置的数据根
Stop.cmd -Home D:\data\superPM  # 显式指定数据根
Stop.cmd -Force                 # 优雅停止失败时强制结束服务进程树
```

- 数据根解析顺序与启动器一致：`-Home` > `SUPERPM_HOME` > `%APPDATA%\superPM\config.json` 指针 > 默认 `%LOCALAPPDATA%\superPM`。
- 默认发送优雅停止请求并等待最多 10 秒；服务本来未运行时直接成功返回，并清理残留的 `runtime\server.json`。
- 存在更新锁或数据目录迁移锁时拒绝执行，避免打断更新或迁移。
- `-Force` 使用 `taskkill /T /F` 结束服务进程树；执行前会校验 PID 命令行确为 superPM 服务入口，无法确认时拒绝结束，避免误杀其他程序。
- 脚本只停止 HTTP 服务，不会结束已连接的 MCP 客户端进程；更新或迁移前请先关闭这些客户端。
- 退出码：`0` 表示已停止或本来未运行；`1` 表示被锁拒绝、优雅停止超时或强制结束失败。双击运行时失败会暂停窗口以显示原因。

已发布的 0.4.0 安装包尚未内置停止脚本。可把仓库 `scripts/install/Stop.cmd` 与 `Stop.ps1` 复制到安装目录（与 `SuperPM.cmd` 同级）后直接使用，无需更新程序或迁移数据。

### 修改数据保存位置

发布安装包中，登录后进入「系统设置 → 本地存储」：

1. 点击「修改保存位置」，选择或手动输入一个绝对路径作为父目录。应用会在其下使用或创建 `superPM` 子目录；父目录可以非空，但不能与当前数据根、安装目录或配置目录互相包含，也不支持 UNC 网络路径。
2. 点击「校验」。页面会展示最终目标路径、待迁移数据量、所需与可用空间、数据库行数与工作区文件数；阻断原因会逐条列出。目标可用空间需覆盖约 1.15 倍数据量加 256 MB 余量。
3. 确认后点击「开始迁移」。服务会停止，迁移助手将 SQLite 在线备份、工作区、`.env` 与 `backups/` 复制到目标暂存目录，逐项校验后原子切换，写入配置指针并重启服务。页面在服务重启期间自动重连并显示阶段与字节进度。
4. 迁移完成后旧数据仍保留，页面会提示处理：默认「保留旧数据」，或经二次确认后「删除旧数据」。删除不可恢复；若仍有旧版本程序或快捷方式指向旧目录，删除后将无法读取原数据。

约束与恢复：

- 迁移期间不要关闭窗口、停止进程或断开目标磁盘；失败时保持原数据根并尽量恢复旧服务。
- 存在 MCP 客户端或更新任务时不能迁移，需先关闭 MCP 或完成更新。
- 开发环境、`SUPERPM_HOME` 显式指定或非发布安装布局下，保存位置只读，页面会显示原因。
- 迁移日志位于配置目录 `logs/move-home-<日期>.log`，任务状态在 `move-home.json`。
- 需要回到默认数据根时，先停止应用，把 `%APPDATA%\superPM\config.json` 改名后重新启动；数据仍在原目录，不会自动删除。

## 3. 端口与配置

环境变量优先级高于数据根 `.env`，数据根 `.env` 高于安装目录 `.env`：

```dotenv
PORT=3001
SUPERPM_WORKSPACE_DIR=workspace
SUPERPM_DATA_DIR=data
# 可选：覆盖版本清单地址，仅允许 HTTPS 且主机在内置允许列表内
SUPERPM_UPDATE_MANIFEST_URL=https://github.com/WangPeng3215/superpm-workbench/releases/latest/download/update-manifest.json
```

更新器在服务已停止时同样读取上述 `.env` 的 `PORT`，并在更新后用同一端口启动新版本。`SUPERPM_UPDATE_MANIFEST_URL` 只影响应用内「检查更新」使用的清单，独立更新器仍以 `--manifest` 参数或内置地址为准。

## 4. MCP 配置

MCP 与 HTTP 服务共用数据根，由客户端以 stdio 拉起：

```json
{
  "command": "D:\\Apps\\superPM\\runtime\\node.exe",
  "args": ["D:\\Apps\\superPM\\app\\apps\\server\\dist\\mcp\\stdio.js"],
  "env": {
    "SUPERPM_MCP_WRITE": "0"
  }
}
```

自定义数据根时额外设置 `SUPERPM_HOME`。默认只开放只读工具；写入能力与安全边界见 [`mcp.md`](mcp.md)。

### AI 客户端 Skill 包（可选）

0.15.0 起，每个 Release 附带 `superpm-skill-<version>.zip`，与安装包同版本，但不参与更新清单，按需手动下载。包内是主入口 Skill 与安装版说明：

```text
superpm/
  SKILL.md
  references/              安装版模式、MCP、原型与任务路由
  docs/mcp.md
  docs/install-update.md
  docs/deployment-update-strategy.md
  INSTALL.txt
```

安装：解压后把 `superpm` 目录放入客户端用户级 skills 目录。

- Qoder：`%USERPROFILE%\.qoder\skills\superpm`
- Claude Code：`%USERPROFILE%\.claude\skills\superpm`
- 其他客户端：放入其支持的 skills 目录，或让 AI 直接读取 `SKILL.md`

Skill 会先区分源码仓库与安装版：安装版读取 `references/install-mode.md`，使用本页的 `SuperPM.cmd` / `Stop.cmd` 与 MCP 配置。Skill 不代替 MCP 配置，也不包含源码仓库脚本；开发任务请使用 Git 仓库中的 `.agents/skills/superpm`。

应用内更新与 `Update.cmd` 只更新 superPM 程序，不会安装或替换 AI 客户端的 Skill。每台设备升级应用后，如需同步文档与规则，请关闭 AI 客户端，下载与应用同版本的 Skill 包，解压后替换 `%USERPROFILE%\.qoder\skills\superpm`（Qoder）或 `%USERPROFILE%\.claude\skills\superpm`（Claude Code），再重新打开客户端；旧目录可先改名备份。多个客户端需要分别替换。

## 5. 更新

发布版优先使用应用内更新：登录后进入「系统设置 → 版本与更新」。安装包内仍保留 `Update.cmd`，用于页面不可用或需要离线更新的场景。

### 应用内更新

1. 点击「检查更新」。服务端读取版本清单，校验产品、平台、schema 与最低更新器版本，并把有效清单缓存到数据根 `updates/available-manifest.json`。
2. 发现新版本时展示版本号、发布日期、更新包大小与更新说明。检测到存活的 MCP 进程时列出进程并默认阻止安装，可显式选择强制更新。
3. 确认后，服务端把更新包下载到 `updates/downloads/<版本>/update.zip`，页面显示下载百分比；下载完成即校验大小与 SHA-256，失败会删除文件并保留当前版本。
4. 校验通过后生成 `updates/install-manifest.json`，其中更新包地址指向本地文件，再以独立进程启动 `bin/updater.mjs`。执行器停止服务、创建更新锁、备份数据、替换 `app/`、执行迁移并重启验证；失败自动回滚。
5. 页面持续轮询 `/api/update/status`。服务重启会短暂断开，页面自动重连；更新成功后自动刷新。执行器把阶段进度写入 `updates/update-progress.json`，各阶段包括 `prepare`、`download`、`verify`、`backup`、`swap`、`migrate`、`restart`、`health` 与 `done`。

应用内更新仅在发布安装包中可用；开发环境可以检查清单，但安装会提示改用 `Update.cmd`。版本清单地址可用 `SUPERPM_UPDATE_MANIFEST_URL` 覆盖，仅允许 HTTPS 且主机在内置允许列表内。

从 0.2.0 使用增量包升级到 0.3.0 时，`bin/updater.mjs` 仍是旧版（增量包只替换 `app/`），不会写入阶段进度；页面会回退到 `updates/last-update.json` 和版本检测。需要完整阶段进度时，请使用 0.3.0 完整安装包重新安装一次。

### 0.3.3 → 0.4.0 一次性 bootstrap

0.4.0 的启动器、更新器和迁移助手新增了配置指针与操作锁逻辑，因此更新器版本由 `1.0.0` 升到 `1.1.0`。0.3.3 自带的更新器 1.0.0 只接受仅含 `app/` 的增量包，无法替换 `bin/`；0.4.0 清单要求 `minUpdaterVersion: "1.1.0"`，所以在 0.3.3 应用内检查到 0.4.0 时会提示更新器版本不足，这是预期行为。

从 0.3.3 升级到 0.4.0 请使用完整安装包：

1. 用 `Stop.cmd` 停止应用（或在启动窗口按 `Ctrl+C`），确认 `runtime\server.json` 已消失。
2. 将 0.4.0 完整包解压覆盖原安装目录，或解压到新目录后改用新目录启动。数据根不在安装目录内，数据不受影响。
3. 若使用新安装目录，更新 MCP 客户端配置中的 `runtime\node.exe` 与 `app\...\stdio.js` 路径。
4. 启动 0.4.0，确认版本与业务数据正常；此后版本恢复应用内增量更新。

发布说明和 `docs/install-update.md` 需要保留这一步说明；清单、`install.json` 与诊断接口的更新器版本均应为 `1.1.0`。

### 0.4.0 → 0.5.0

0.5.0 没有启动器或更新器变更，已安装 0.4.0 的用户可在「系统设置 → 版本与更新」直接增量升级。更新器会先创建 `pre-update` 备份，再替换程序并自动执行 schema 14 的每日任务表迁移，随后重启并检查健康状态；重启期间页面会短暂离线。

增量包只替换 `app/`，不会补装安装目录根下的 `Stop.cmd` 与 `Stop.ps1`。需要这两个停止脚本时，下载 0.5.0 完整包，先用现有方式停止服务，再覆盖安装目录并双击 `SuperPM.cmd` 启动；数据根与业务数据不受影响。0.3.3 或更早版本仍必须先按上一节用 0.4.0 完整包完成 bootstrap。

### 命令行更新（备用）

```powershell
Update.cmd --manifest https://github.com/WangPeng3215/superpm-workbench/releases/latest/download/update-manifest.json
```

常用参数：

| 参数                    | 作用                                  |
| ----------------------- | ------------------------------------- |
| `--json`                | 结果以 JSON 输出，过程日志写入 stderr |
| `--force`               | MCP 或服务超过 15 秒未退出时强制结束  |
| `--no-restart`          | 替换与迁移后不启动服务                |
| `--home <目录>`         | 覆盖数据根                            |
| `--install-root <目录>` | 覆盖安装目录                          |

更新器会先把自身复制到系统临时目录再执行，避免替换 `app/` 时被当前进程占用。执行流程：

1. 读取并校验清单：产品名、平台、版本只能升高、schema 不允许降级、最低更新器版本、更新包 SHA-256 与大小。
2. 写入更新锁；MCP 心跳发现锁后自行关闭；请求 HTTP 服务优雅退出。
3. 等待 MCP 退出，默认 15 秒；超时需显式 `--force`，否则中止更新。
4. 下载更新包到数据根 `updates/`，校验摘要与大小，安全解压并检查包内版本与 schema。
5. 通过备份工具创建 `pre-update` 备份（数据库、工作区、数据根 `.env`）。
6. 将 `app/` 改名为 `app.previous`，换入新程序；执行数据库迁移。
7. 启动新版本并轮询健康检查，核对 PID、版本、schema 与数据库状态；通过后释放更新锁。

每个阶段都会更新 `updates/update-progress.json`；应用内页面据此展示进度，页面刷新后仍可恢复状态。更新源仅允许 HTTPS，且主机必须在更新器内置允许列表中（GitHub 与 GitHub Release 资源域名）。本地清单与本地更新包只用于离线演练，不改变线上校验规则。

### 更新结果

结果写入 `updates/last-update.json`，同时追加到 `logs/update.log`。

| 状态              | 含义                                       | 服务状态                                   |
| ----------------- | ------------------------------------------ | ------------------------------------------ |
| `updated`         | 新版本已完成替换、迁移与健康检查           | 新版本运行中（`--no-restart` 时保持停止）  |
| `failed`          | 替换前失败（下载、摘要、解包、备份等）     | 未指定 `--no-restart` 时旧版本自动恢复运行 |
| `rolled-back`     | 替换或迁移后失败，已恢复旧程序与更新前数据 | 未指定 `--no-restart` 时旧版本自动恢复运行 |
| `rollback-failed` | 回滚本身失败，更新锁保留                   | 需手动处理                                 |

`failed` 与 `rolled-back` 都会保留更新前备份。`rolled-back` 还会把更新失败时产生的工作区改名保留为 `workspace.update-failed-<时间戳>`，避免覆盖现场。

### 强制更新

服务或 MCP 未在 15 秒内退出时，加 `--force` 会强制结束相关进程。已知影响：

- 正在执行的 MCP 调用会失败，需要重试。
- 未提交事务丢失；已提交数据由更新前备份兜底。
- 客户端可能需要重连或重启才能恢复 MCP 工具列表。

## 6. 回滚与手动恢复

正常升级失败时更新器自动回滚。需要手动回退到上一版本时：

1. 停止 HTTP 服务与所有 MCP 客户端，确认 `runtime\server.json` 已消失。
2. 在安装目录中把当前 `app` 改名为 `app.failed`，把 `app.previous` 改名为 `app`。
3. 在数据根运行对应版本的备份工具恢复 `pre-update` 备份：

```powershell
D:\Apps\superPM\runtime\node.exe D:\Apps\superPM\app\apps\server\dist\backup-cli.js list
D:\Apps\superPM\runtime\node.exe D:\Apps\superPM\app\apps\server\dist\backup-cli.js verify <备份ID>
D:\Apps\superPM\runtime\node.exe D:\Apps\superPM\app\apps\server\dist\backup-cli.js restore <备份ID>
```

4. 双击 `SuperPM.cmd` 启动旧版本，确认页面与业务数据正常。
5. 仅在确认无更新进程仍在使用后删除 `runtime\update.lock`；不要删除 `last-update.json`、失败工作区或备份，便于定位原因。

若 `app.previous` 已被后续成功更新清理，只能重新解压上一正式版本的完整安装包；用户数据仍在数据根，不受影响。


脚本默认构建当前版本的完整包，解压到临时安装目录，用配置指针启动服务并写入需求、工作区文件、附件与备份，然后通过接口完成 `A → B` 迁移、删除旧数据、`B → C` 反向迁移、保留旧数据、`C → D` 再次迁移，逐次校验配置指针、`previousHome`、数据库、工作区、备份、迁移标记、锁释放与重启后的健康状态。

`bootstrap` 场景会下载 v0.3.3 完整包（可用 `--from-033 <zip>` 指定本地文件），写入示例数据后确认 0.3.3 更新器因最低版本要求拒绝 0.4.0 增量升级；随后用 0.4.0 完整包覆盖安装目录，验证数据根与业务数据不变，且 `/api/update/status` 报告更新器 `1.1.0`。加 `--keep` 保留演练目录，失败时目录也会保留以便查看日志。

## 8. 已知边界

- 更新包尚未做数字签名；SHA-256 与 HTTPS 只能防传输损坏和错误来源，不能替代发布者签名。签名校验在后续阶段评估。
- 更新器不支持自升级。清单中的 `minUpdaterVersion` 高于本地更新器时，必须重新下载完整安装包。
- 发布源使用 GitHub Release；无自建更新服务器。
- 应用内更新仅在发布安装包中可用；开发环境使用 `Update.cmd` 或完整安装包。服务重启期间页面会短暂离线，更新结果以 `updates/last-update.json` 和新版本号为准。
- 数据根迁移只复制数据库、工作区、`.env` 与 `backups/`；`logs/`、`runtime/`、`updates/` 由新数据根重新生成。旧目录中的日志与更新缓存不会迁移，需要时请从旧目录留存。
- 迁移目标必须是本地绝对路径；不支持 UNC 网络路径。网络映射盘可迁移，但迁移后必须保持连接，否则启动保护会拒绝以空目录启动。
- 配置指针是普通 JSON 文件，不加密。需要回到默认目录或指针损坏时，停止应用后把 `config.json` 改名即可；应用不会根据旧指针自动删除任何数据。
- 删除旧数据只处理当前记录中的 `data`、`workspace`、`backups` 与 `.env`，且必须匹配任务 ID、旧数据根与旧目录标记；不会递归删除旧目录中的其他文件。
